เอกสารสถาปัตยกรรมระบบ

Flight Operation — โครงสร้างเว็บแอป

ระบบจัดบินรายวันของฝูงบิน (ฝูง.603 บน.6) สำหรับผู้ใช้ ~100 คน — จัดภารกิจ, คิวบิน, สถานภาพเครื่อง, รายงานหลังบิน, ชั่วโมงบินสะสม และสถิติ · ต้นทุนโครงสร้างพื้นฐานเป้าหมาย ฿0

เทคโนโลยี สถาปัตยกรรม การล็อกอิน Data Flow หน้าเว็บ ฐานข้อมูล สิทธิ์ผู้ใช้ การ Deploy

1ภาษาและเครื่องมือที่ใช้

เว็บแบบ static ล้วน (ไม่มี build step / ไม่มี framework) + backend สำเร็จรูป Supabase

🖥️ Frontend

  • Vanilla JavaScript (ES Modules, import ตรง ไม่มี bundler)
  • HTML5 + CSS3 (CSS variables, รองรับธีมสว่าง/มืด)
  • Supabase JS SDK v2 โหลดจาก esm.sh CDN
  • ฟอนต์: Google Fonts (Bai Jamjuree, IBM Plex Sans Thai/Mono)

🗄️ Backend (BaaS)

  • Supabase — PostgreSQL 15
  • Auth: Google OAuth (Sign in with Google)
  • RLS (Row Level Security) บังคับสิทธิ์ระดับฐานข้อมูล
  • Triggers + Functions (PL/pgSQL) คิดชั่วโมงบิน/สถานะอัตโนมัติ

☁️ Hosting / Deploy

  • GitHub Pages — เสิร์ฟไฟล์ static จาก branch main
  • Repo: greensupawich/flight-operation
  • Dev server ท้องถิ่น: static-server.cjs (พอร์ต 5510)
  • ไม่มีเซิร์ฟเวอร์ backend ของตัวเอง (ทุกอย่างผ่าน Supabase)

2ภาพรวมสถาปัตยกรรม

เบราว์เซอร์โหลดไฟล์ static จาก GitHub Pages แล้วคุยกับ Supabase โดยตรงผ่าน HTTPS (REST/Realtime) — ทุก request ถูกกรองด้วย RLS ตาม role ของผู้ใช้

ผู้ใช้ (Client)
เบราว์เซอร์โหลด HTML/CSS/JS · เก็บ session (JWT)
Google OAuthยืนยันตัวตนด้วยบัญชี Google
Hosting
GitHub Pagesไฟล์ static (12 หน้า HTML + 14 JS module)
ไม่มีโค้ดฝั่งเซิร์ฟเวอร์ · deploy = git push
Backend — Supabase
Authจัดการ session + Google OAuth callback
PostgreSQL + RLS19 ตาราง · policy กรองตาม role
Triggers / Functionsคิด ชม.บิน, currency, สถานะ อัตโนมัติ

🔑 Anon key อยู่ในโค้ดฝั่ง client ได้อย่างปลอดภัย เพราะข้อมูลถูกป้องกันด้วย RLS ทั้งหมด — ไม่มี service-role key หรือรหัสลับใด ๆ ในไฟล์ที่ deploy

3ขั้นตอนการล็อกอิน & อนุมัติผู้ใช้

ผู้ใช้คนแรกของระบบถูกตั้งเป็น admin อัตโนมัติ · คนถัดไปต้องรอ admin อนุมัติก่อนเข้าใช้งาน

1 · เข้า index.htmlกด "Sign in with Google"
→
2 · Google OAuth→ Supabase สร้าง session + profile
→
3 · เช็ค statustrigger handle_new_user ตั้งค่าเริ่มต้น
→
4 · เข้าใช้งานactive → home.html · pending → pending.html
กรณีผลลัพธ์
ผู้ใช้คนแรกของระบบตั้งเป็น admin + active ทันที (trigger)
ผู้ใช้คนถัดไปสร้างเป็น pending + viewer → เด้งไป pending.html ให้กรอกชื่อ/ตำแหน่งขอใช้งาน
admin อนุมัติตั้ง role + status=active ที่หน้า admin.html → ผู้ใช้เข้าระบบได้

4กลไกหัวใจ — บันทึกรายงานหลังบิน 1 ครั้ง

เมื่อผู้ใช้บันทึก post_flight_reports (ยืนยันว่าบินจริง) Postgres triggers จะกระจายข้อมูลไปหลายตารางอัตโนมัติ — ไม่ต้องกรอกซ้ำ และกันข้อมูลเพี้ยน

💾 บันทึกรายงานหลังบินpost_flight_reports
(INSERT / UPDATE)
→
crew_hoursบวก ชม.บินรายคน (IP/P/CP) · ผูกกับรหัสนักบิน
→
aircraft.total_hoursบวก ชม.สะสมของเครื่องลำนั้น
→
crew_members.last_500/600_dateอัปเดตวันบินล่าสุดตามแบบเครื่อง (trigger bump_crew_currency)
→
discrepanciesข้อขัดข้องหลังบินผูกกับเครื่อง

อีกชุดหนึ่ง: เมื่อแก้ สถานภาพเครื่อง (aircraft.status) → trigger snapshot_aircraft_status บันทึกลง aircraft_status_history เป็นประวัติรายวัน (ใช้ดู/แก้ย้อนหลังได้)

8การ Deploy & สภาพแวดล้อม

🚀 Deploy

  • git push ขึ้น branch main
  • GitHub Pages build อัตโนมัติ (~1 นาที)
  • Live: greensupawich.github.io/flight-operation

🔧 Supabase config

  • Auth → URL Configuration: ใส่ Site URL + Redirect (/**)
  • Google Cloud OAuth client (callback = Supabase)
  • รัน migration SQL ใน SQL Editor (schema → policies → triggers → migrations)

💻 พัฒนาในเครื่อง

  • node static-server.cjs → localhost:5510
  • เพิ่ม localhost:5510/** ใน Redirect URLs เพื่อทดสอบ OAuth
  • ไม่ต้องมี build/compile

  • GitHub Pages: ฟรี
